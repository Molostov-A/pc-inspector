## 1. Что это за проект (30 секунд)

Локальное Windows-приложение на Python: сканирует диски в SQLite-индекс и показывает,
чем занято место, что является мусором, дубликатами, забытыми файлами и неиспользуемыми программами.
Помогает составить **план уборки**, который выполняет **только человек**, с откатом.
Интерфейсы: веб-UI (FastAPI + ванильный JS + ECharts, без сборки), CLI, MCP-сервер для ИИ.

## 2. Текущее состояние кода

Этапы 0–7 реализованы и покрыты тестами, этап 8 открыт (см. ROADMAP). Данные лежат в двух базах (`core/db.py`):
скан пишет в индекс, планы и коллекторы — в `<индекс>.state.db`. Логика разделена по модулям пакета `services/`.

## 3. Архитектура — жёсткие правила

```
cli.py / api/ / mcp_server.py   ← только парсинг ввода и форматирование вывода
            │
        services/               ← единственная точка входа в логику
            │
analyzers/  collectors/  actions/  core/scanner
            │
core/ (db, models, safety, fmt, jobs), config.py
```

1. **Зависимости только вниз.** `core` не импортирует `analyzers`, `actions`, `api` и т. д.
2. **В интерфейсах нет SQL и бизнес-логики.** Нужно что-то новое в UI — добавьте функцию в `services/`.
3. **Анализаторы только читают** (read-only соединение), не трогают ФС и ничего не пишут в БД.
4. **ФС изменяет только `actions/executor.py`.** `os.remove`, `shutil.rmtree`, `shutil.move`, `send2trash`, `Path.unlink` где-либо ещё — запрещены.
   Исключение: сканер и коллекторы читают ФС; `config` создаёт `data/`.
5. **Проверки безопасности путей — только в `core/safety.py`.** Не дублировать список защищённых папок.
6. **Единый формат результата — `Report`/`Finding`** (`core/models.py`). Не придумывайте свои структуры ответа.
   Размеры — int байт, даты — unix timestamp; форматирование — только в интерфейсе.
7. Новые зависимости — только из списка ТЗ §4; иначе запись в DECISIONS.md с обоснованием.

## 4. Инварианты безопасности (нарушение = блокирующий баг)

- Нет безвозвратного удаления (только корзина / карантин / перемещение). Очистку карантина запускает человек.
- **MCP не получает инструментов, меняющих ФС** (execute, delete, move, restore). Никогда, даже «для удобства».
- Выполнение плана — только с подтверждением человека (токен в UI, `yes`/`--yes` в CLI).
- Защищённые зоны проверяются и при добавлении в план, и перед выполнением.
- Перед действием сверить `size`/`mtime` с моментом анализа; изменилось — пропустить.
- Веб-сервер — только `127.0.0.1`, мутирующие запросы с `X-PCI-Token` и проверкой `Origin`.
- **Тесты и отладка не трогают реальные диски пользователя**: только `tmp_path`, временная БД (`PCI_DB`),
  подменённый `send2trash`. Никогда не запускайте executor на реальных путях при разработке.

## 5. Рецепты расширения

### 5.1. Новый анализатор
1. Создать `pcinspector/analyzers/<module>.py` (или дописать в тематический модуль).
2. Класс-наследник `Analyzer` с `@register`: `id` (snake_case, стабильный — это публичный API), `title`,
   `description` (1–2 предложения, их читает ИИ через MCP), `params` (переиспользуйте `P_LIMIT`, `P_ROOT`, `P_MIN_SIZE`).
3. `run(self, con, **params) -> Report`. Используйте `root_filter()` для параметра `root`.
   Всё необходимое для понимания находки кладите в `reason` (по-русски, для человека) и `meta`.
4. Добавить импорт модуля в `analyzers/__init__.py`.
5. Тест в `tests/test_analyzers_<module>.py` на фикстуре `fake_tree`.
6. **Больше ничего не трогать**: CLI, API, MCP и страница «Анализаторы» подхватят его сами.
   Отдельный экран в UI — только если это предусмотрено ТЗ.

### 5.2. Новое правило мусора
Только данные в `analyzers/rules.toml` (`[[dir_name]]`, `[[dir_path]]`, `[[file]]`). Поля: `id`, `title`, `safety`, `hint` + условие. Для активных кэшей добавляйте `"action": "clear_contents"`. Точные пути срабатывают раньше правил по имени.
В SQL `LIKE` подстановочный символ одной буквы — `_` (не `?`). `safe` ставить только для того,
что гарантированно восстанавливается само (кэш, temp). Сомневаетесь — `review`. Добавить кейс в тест `junk`.

### 5.3. Изменение схемы БД
Только через новую миграцию в `core/migrations.py` (+1 к `PRAGMA user_version`), идемпотентно.
Обновить §6.2 в SPEC.md. Таблицы `file_hashes`, `apps`, `plans`, `actions_log` переживают пересканирование — не удаляйте их данные.

### 5.4. Новый эндпоинт API / инструмент MCP
Сначала функция в `services/`, затем тонкая обёртка в `api/routes/*.py` (Pydantic-схемы в `api/schemas.py`)
и/или в `mcp_server.py`. Для MCP: описание инструмента — по-английски, кратко, с указанием ограничений.
Мутирующий ФС инструмент в MCP добавлять нельзя (§4).

### 5.5. Новый экран UI
`web/js/pages/<name>.js` экспортирует `render(container, params)`; зарегистрировать маршрут в `web/js/app.js`.
Все запросы — через `web/js/api.js` (он добавляет токен). Общие компоненты (`reportTable`, `sizeBar`, `safetyBadge`,
`treemap`) — в `web/js/components/`. Никаких фреймворков и сборщиков; ECharts — из `web/vendor/`.

## 6. Соглашения по коду

- Python 3.11+, type hints везде, `from __future__ import annotations`.
- Идентификаторы и имена — по-английски; **docstring, комментарии, тексты UI и сообщения — по-русски**.
- Docstring у каждого модуля: роль модуля в архитектуре в 1–3 строки.
- `ruff` (line-length 110), `ruff format`. Без `print` в библиотечном коде — `logging` (кроме `cli.py`).
- Пути Windows: сравнивать без учёта регистра (`COLLATE NOCASE` в SQL, `.lower()`/`os.path.normcase` в Python);
  в БД хранить пути в нативном виде с `\`, без завершающего слеша (кроме корня диска `C:\`).
- SQL — только параметризованный (`?`). Подстановка строк в SQL допустима лишь для имён из констант кода.
- Большие выборки — с `LIMIT`; ничего не грузить в память целиком, кроме агрегатов.

## 7. Окружение и команды (Windows, PowerShell)

```powershell
cd B:\Programm\pc-inspector
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev]"

python -m pytest -q                       # тесты
ruff check . ; ruff format --check .      # линт
$env:PCI_DB = "$env:TEMP\pci-dev.db"      # отдельная БД для ручных проверок
python -m pcinspector scan B:\Programm    # безопасный небольшой корень для ручной проверки
python -m pcinspector junk --json
python -m pcinspector serve --open
```

## 8. Процесс работы над задачей

1. Взять **первую** невыполненную задачу текущего этапа в ROADMAP (не прыгать между этапами).
2. Перечитать связанные требования SPEC по их ID.
3. Реализовать + тесты. Запустить `pytest` и `ruff`.
4. Отметить задачу `[x]` в ROADMAP, при необходимости дописать заметку.
5. Нетривиальное решение (выбор библиотеки, отклонение от ТЗ, компромисс) — 3–5 строк в DECISIONS.md:
   дата, контекст, решение, последствия.
6. Коммит: `<этап>: <что сделано> (F2.1, N8)`. Один логический шаг — один коммит.

**Definition of Done задачи:** код соответствует ТЗ; тесты есть и зелёные; ruff чистый; инварианты §4 не нарушены;
ROADMAP обновлён; если менялись CLI/API/MCP — обновлён README.

## 9. Чего не делать

- Не переписывать архитектуру и не менять стек «потому что так лучше» — сначала DECISIONS.md и согласование с пользователем.
- Не добавлять npm/сборку фронтенда, ORM, фоновые очереди (Celery и т. п.), Electron.
- Не удалять и не перемещать файлы пользователя ни в каком коде, кроме executor; не запускать executor на реальных путях.
- Не требовать прав администратора для базовых функций; при их отсутствии — деградация с пояснением в `notes`.
- Не отправлять данные в сеть. Не добавлять телеметрию и автообновления.
- Не оставлять задачи «почти сделанными»: либо `[x]` с тестами, либо явная заметка в ROADMAP, что осталось.
